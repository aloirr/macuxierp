# T-0030 — Desenho: troca da filial para produção fiscal só pelo operador

- **Dono:** engenheiro-software · **Data:** 21/11/2026, 21h20 (Manaus) · **Fase:** F1, antes do deploy (T-0024)
- **Decisão:** ADR 0006, opção (a).
- **Fontes:** `CLAUDE.md` (regra 7); RN-CORE-08; T-0002 (D12, seção 2); ADRs 0004 e 0005; `modules/core/{domain/ambiente.ts,contracts/index.ts,api/rotas.ts,api/portas.ts,api/repositorio-sql.ts,web/*}`; `db/migrations/0003_core.sql`; `scripts/plataforma/licenca.mjs`.

## 1. Problema
Hoje a rota `PUT /v1/core/ambientes-fiscais/:filial_id` aceita `{ ambiente: "producao", recado_aprovacao: "R-…-alexandre" }` e só confere o **formato** do id. Isso acontece no domain (`avaliarTrocaAmbiente`) e no banco (CHECK `ambiente_producao_aprovada`). Com isso, um administrador do cliente põe a filial em produção sem a aprovação do Alexandre (regra 7).

## 2. Resumo da solução
| Caminho | Homologação → produção | Produção → homologação |
|---|---|---|
| Rota do tenant (`core.ambiente.trocar`, adm) | **422 `RN-CORE-08`**; o banco também recusa (RLS) | permitido, auditado, com evento, sem aprovação |
| Script do operador `scripts/plataforma/ambiente-fiscal.mjs` | permitido só com o arquivo do recado "aprovo produção fiscal <empresa>" do Alexandre conferido; auditado, com evento | permitido, com `--motivo`, auditado, com evento |

## 3. Etapa 2 — modulo-core

### 3.1 Domain (`modules/core/domain/ambiente.ts`)
A função `avaliarTrocaAmbiente` dá lugar a `avaliarTrocaAmbienteTenant`, uma função pura, com o teste escrito antes:
```ts
/** RN-CORE-08: pelo tenant, só se volta (ou fica) em homologação; a ida para produção é do operador (ADR 0006). */
export function avaliarTrocaAmbienteTenant(t: { atual: Ambiente | null; novo: Ambiente }):
  | { ok: true; ambiente: 'homologacao'; muda: boolean }
  | { ok: false; mensagem: string };
```
- `novo = 'producao'` dá `ok: false`, com a mensagem "A troca para produção fiscal é feita pela Macuxi, com a aprovação do Alexandre". Vale para qualquer `atual`, inclusive `producao`: o tenant não regrava produção.
- `novo = 'homologacao'` dá `ok: true`. `muda` fica `false` só quando `atual = 'homologacao'`. Com `atual = null`, sem linha, `muda` fica `true`: a linha nasce em homologação, o que é inofensivo e deixa o registro explícito.
- O domain deixa de importar `PADRAO_RECADO_APROVACAO`.

### 3.2 Contracts (`modules/core/contracts/index.ts`)
- `AmbienteTrocar = z.object({ ambiente: z.enum(['homologacao', 'producao']) })`. O `recado_aprovacao` sai do corpo. Campo extra é descartado pelo Zod, então cliente antigo não quebra.
  - O enum continua com `producao` de propósito: o pedido de produção chega ao domain e recebe **422 `RN-CORE-08`**, com a regra citada, em vez de um 400 `VALIDACAO` mudo.
- `AmbienteFiscal`, a resposta, **não muda**. Ela continua com `recado_aprovacao` (nulo em homologação), para a tela mostrar qual recado aprovou a produção.
- O `PADRAO_RECADO_APROVACAO` sai de `contracts`, porque nenhum módulo usa mais. A regex passa a viver no script, que tem um teste comparando com o CHECK de `0003_core.sql`.
- O evento `core.ambiente_fiscal.alterado@1` fica **igual**: mesmo payload `{ filial_id, ambiente, recado_aprovacao }` e mesma versão. Não há aviso de contrato.

### 3.3 Rota (`modules/core/api/rotas.ts`)
`PUT /ambientes-fiscais/:filial_id`, ação `core.ambiente.trocar` (só administrador, sem mudança em `permissoes.ts`):
1. Lê a linha atual (`repo.ambientes`).
2. Chama `avaliarTrocaAmbienteTenant`. Se vier `ok: false`, responde `erros.regra('RN-CORE-08', mensagem)` (422) e não grava, não audita nem publica nada.
3. Se `muda = false`, responde 200 com a linha atual e não grava, não audita nem publica. É idempotente.
4. Se `muda = true`, grava `{ ambiente: 'homologacao', recado_aprovacao: null, alterado_por: usuario }`, audita `core.ambiente.trocado` com `antes: { ambiente, recado_aprovacao }` e `depois: { …dto, origem: 'api' }`, publica o evento e responde o DTO.

### 3.4 Porta e repositório
- `RepositorioCore.gravarAmbiente` passa a receber `LinhaAmbiente & { ambiente: 'homologacao'; alterado_por: string }`. O tipo impede o core de pedir produção.
- `repositorio-sql.ts`: o SQL continua o mesmo. Se alguém forçar `producao`, o banco recusa (seção 5).
- `repositorio-memoria.ts`: o `gravarAmbiente` lança erro se receber `producao`, imitando a RLS. Assim, o teste de rota prova que o core nunca tenta.

### 3.5 Web (`modules/core/web/cliente.ts`, `paginas.ts`)
- `trocarAmbiente(filialId)` passa a só voltar para homologação, com o corpo `{ ambiente: 'homologacao' }`.
- A página "Ambiente fiscal" mostra o ambiente e o recado registrado.
  - Em homologação, mostra o texto "Para emitir em produção, peça à Macuxi. A troca é feita com a aprovação do Alexandre." e não tem botão de produção.
  - Em produção, tem o botão "Voltar para homologação", com confirmação.
- Muda texto e tira um botão; não muda cor nem layout. Se mudar o layout, vai à validação do `design-de-marca` (regra 7 da definição de pronto).

## 4. Etapa 2 — engenheiro-software: script do operador
Arquivo `scripts/plataforma/ambiente-fiscal.mjs`, no molde do `licenca.mjs`: funções puras exportadas, `executar(cliente, op, agora)` testável com um cliente pg falso, `main` só com a conexão. A conexão é a `MACUXIERP_DATABASE_URL_OPERADOR`, o admin do DBaaS e dono das tabelas, sem `FORCE RLS`.

### 4.1 Uso
```
node scripts/plataforma/ambiente-fiscal.mjs listar      --empresa <slug>
node scripts/plataforma/ambiente-fiscal.mjs producao    --empresa <slug> --filial <uuid> --recado <R-…-alexandre> --arquivo-recado <caminho .md> --operador <nome> [--confirmar]
node scripts/plataforma/ambiente-fiscal.mjs homologacao --empresa <slug> --filial <uuid> --operador <nome> --motivo "<texto>" [--confirmar]
```
Sem `--confirmar`, o script só simula: abre a transação, mostra o plano e faz rollback.

### 4.2 O que confere
**Decisão:** o script confere o texto do recado. Não basta o operador olhar. O arquivo é obrigatório e vem do repositório de recados. O operador baixa o arquivo onde tiver acesso, por exemplo com `gh api repos/aloirr/macuxierp-recados/contents/recados/<destino>/<id>.md -H "Accept: application/vnd.github.raw" > <arquivo>`, e o passa em `--arquivo-recado`. O servidor não precisa de token do GitHub.

1. **Argumentos** (`ErroUso`, saída 2):
   - o slug da empresa (`^[a-z0-9][a-z0-9-]{1,39}$`) e o `--filial` como UUID;
   - o `--operador` (`^[a-z][a-z0-9._-]{1,39}$`);
   - em `homologacao`, o `--motivo` com pelo menos 5 caracteres;
   - em `producao`, o `--recado` casando com `^R-\d{8}-\d{6}(-\d+)?-alexandre$` (a mesma regex do CHECK) e o `--arquivo-recado`. O `--motivo` é opcional, e o motivo é o recado.
2. **O arquivo do recado** (`conferirRecado(texto, nomeArquivo, op, tenant, ativos)`, função pura):
   - o nome do arquivo (basename) é `<id>.md`;
   - o cabeçalho YAML tem `id: <id>` e `de: alexandre`;
   - o texto, normalizado (NFD sem acentos, minúsculas, espaços colapsados), contém `aprovo producao fiscal <empresa>`. Vale como `<empresa>` o slug do tenant ou o nome do tenant normalizado, seguidos de fim de linha, de espaço ou de pontuação que não seja `-`. O texto é conferido contra todos os tenants ativos e só vale se o casamento mais longo for deste tenant ("Thathyany Manaus Ltda" ou `thathyany-manaus` não aprovam o tenant `thathyany`);
   - qualquer divergência dá erro com o motivo (por exemplo, "o recado não aprova <slug>", sem trecho do texto do recado) e nada é gravado.
3. **O tenant e a filial**, na transação, com `set_config('app.tenant_id', …, true)`:
   - o tenant vem de `select id, slug, nome from plataforma.tenant where slug = $1 and situacao = 'ativo' and deleted_at is null`. **Não** usar `tenant_por_slug()` (ver 4.5);
   - a filial precisa existir em `cadastros.filial_resumo` desse tenant. Filial de outro tenant ou inexistente dá erro;
   - o certificado ativo e válido da filial (`core.certificado`, só o resumo) entra como **aviso** na saída, não como bloqueio: a emissão já barra A1 vencido (RN-CORE-06).
4. **Idempotência:** a linha é lida com `for update`.
   - `producao` com a filial já em produção: "nada a mudar", mostrando o recado já registrado. Para trocar o recado, o operador volta e vai de novo.
   - `homologacao` com a filial já em homologação ou sem linha: "nada a mudar".
   - Em "nada a mudar", não há auditoria nem evento.

### 4.3 O que grava (mesma transação; com `--confirmar`, commit, senão rollback)
1. `insert … on conflict (tenant_id, filial_id) do update` em `core.ambiente_fiscal`:
   - para produção: `ambiente`, `recado_aprovacao` = id e `alterado_por = null`;
   - para homologação: `recado_aprovacao = null`;
   - nos dois casos, `deleted_at = null`.
2. Uma linha em `plataforma.auditoria`:
   - `usuario_id` nulo, `acao` `core.ambiente.trocado` (a mesma da rota, para o `GET /v1/core/auditoria` do cliente mostrar), `entidade` `ambiente_fiscal` e `entidade_id` = filial;
   - `antes { ambiente, recado_aprovacao }`;
   - `depois { filial_id, ambiente, recado_aprovacao, origem: 'script', operador, motivo?, recado_sha256 }`;
   - `request_id` `operador-<uuid>`.
3. Uma linha em `plataforma.evento`: `core.ambiente_fiscal.alterado@1`, com `agregado_id` = filial, `versao` = ms UTC de `agora` (igual à rota) e o payload `{ filial_id, ambiente, recado_aprovacao }`.

### 4.4 Saída
- O plano em JSON: empresa, filial, antes, depois e avisos.
- Em seguida, uma destas mensagens: `aplicado e auditado.`, `nada a mudar.` ou `SIMULAÇÃO: nada gravado. Repita com --confirmar para aplicar.`
- Códigos de saída iguais aos do `licenca.mjs`: 0 deu certo, 1 falha, 2 uso.
- O texto do recado não aparece no terminal, só o id e o SHA-256. Erro de banco mostra só o `e.name` e o `code`, sem dado.

### 4.5 Junto, no mesmo lote
Correção do `licenca.mjs`: ele chama `select id, nome from plataforma.tenant_por_slug($1)`, mas a função devolve só o `uuid` (0002). No banco de verdade o script falha, e o teste não pega porque usa um cliente falso. Trocar `tenant_por_slug()` pela mesma consulta de `plataforma.tenant` do script novo e ajustar o cliente falso do `licenca.test.mjs`. Também atualizar o comentário de `core.ambiente.trocar` em `packages/platform-sdk/src/permissoes.ts` para: "só volta para homologação; produção é do operador, ADR 0006".

## 5. Etapa 2 — banco-dados: migração `db/migrations/0008_ambiente_fiscal_operador.sql`
**Vale a garantia no banco?** Sim. O custo é baixo e ela fecha o caminho que sobraria: um bug ou um SQL novo no core gravando `producao`. Duas formas foram avaliadas:
- **trigger** que olha o `current_user`: funciona, mas é código procedural e depende de uma lista de nomes de papel;
- **política RLS restritiva**, declarativa e por papel. **É esta a escolhida.**

```sql
-- Regra 7 / RN-CORE-08 / ADR 0006: o app só grava homologação; produção só pelo operador (dono da tabela, sem FORCE RLS).
CREATE POLICY app_so_homologacao_ins ON core.ambiente_fiscal AS RESTRICTIVE FOR INSERT TO macuxierp_app
  WITH CHECK (ambiente = 'homologacao');
CREATE POLICY app_so_homologacao_upd ON core.ambiente_fiscal AS RESTRICTIVE FOR UPDATE TO macuxierp_app
  USING (true) WITH CHECK (ambiente = 'homologacao');
```
- A migração deve ser reexecutável: `DROP POLICY IF EXISTS` antes de cada `CREATE`.
- O `isolamento_tenant` (permissiva) continua, e as duas políticas valem juntas.
- O `macuxierp_worker` e o `macuxierp_leitura` só têm SELECT nessa tabela, então não precisam de política.
- O `INSERT … ON CONFLICT DO UPDATE` da API passa pela política de UPDATE, e a linha nova precisa ser homologação.
- **O CHECK `ambiente_producao_aprovada` fica como está.** Ele já exige o recado no formato certo em produção, e o script sempre o informa. Não há coluna nova: origem, operador e hash ficam na auditoria.
- Também na 0008: corrigir o comentário das linhas 51 e 52 de `0003_core.sql` com um `COMMENT ON TABLE core.ambiente_fiscal`. A migração antiga não se edita.
- Pré-requisito que o banco-dados confere: o papel das migrações e do operador é o **dono** de `core.ambiente_fiscal` e não tem `FORCE ROW LEVEL SECURITY` (o `controle.preparar_tabela` não força). Se o DBaaS mudar isso, o script do operador passa a cair na RLS e o teste de banco da seção 6 acusa.
